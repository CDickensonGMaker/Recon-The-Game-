- **One suppressor slot** re-elected on a 1.2s cadence (`SUPPRESSOR_REFRESH_MS`), prefers a

- **SUPPRESS_TARGET finally has an executor on BOTH sides**: the no-LOS branch of
  `_execute_combat` fires on the squad's last-known cell from where the man stands
  (`enemy_base.gd` "THE SUPPRESSOR SLOT EXECUTES", `ally_base.gd` same banner). Area
  suppression falls out of `CombatManager.suppress_along_shot` on the real rounds.

  from where he is. SEEK_COVER / RETREAT never touch the pool — orders stay refusable.
  Token TTL + member TTL guard stuck tokens (the R3 named sacrifice).

  `EnemySquad.report_firing`/`has_covering_fire` are DELETED (fossil law), replaced by

## Phase 3 — bounding overwatch (as built)
Two elements by registration-order parity (`register`), alternating on the doctrine's
`bound_period_ms` (`_update_elements`): only the ACTIVE element draws fresh exposure
tokens while the fight is live, grants staggered by `grant_stagger_ms`, and the suppressor
prefers the PASSIVE element. Element A moves under element B's base of fire, then they
swap — expressed entirely through the token machinery, no order queue, O(1) per man.

## Deviations from the synthesis, named
- "One autoload per side" shipped as ONE static registry in EnemySquad's idiom (TTL-lazy
  recompute, all time passed as now_ms). Same O(1)/man + ~1Hz squad-tick cost, no
  node lifecycle, probe-drivable clock, cleared in `MissionScope.reset()`.
- The cover-claim table stays in `EnemyBase._cover_claims`: it is already ONE shared
  broker for both sides keyed by world cell, and claims are correctly global-by-cell
  (two squads must not stack one rock). Folding it into per-squad records would have
  changed behaviour the decree did not ask to change.
